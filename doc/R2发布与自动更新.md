# R2 发布与设备自动更新

## 目标与边界

slaveSim 沿用上位机的 Cloudflare R2 存储桶与参数名称，独立使用 `slavesim` 对象前缀。同时提供 Linux amd64、arm64 的二进制包与 Docker 镜像包。设备上的独立更新程序周期检查清单，校验后更新由本项目 Compose 管理的模拟器，健康检查失败时回退。

本次只接入代码与 GitHub 发布，不在真机或模拟服务器启用更新任务。更新程序不改动下位机、不重启其他服务、不覆盖现有配置或日志，也不接管以其他方式启动的容器。

## 发布触发与路径

- 推送 `master`：发布 `ci` 通道，版本为 `0.0.0-ci.<run_number>.<run_attempt>`。
- 推送正式版本标签 `vX.Y.Z`：发布 `stable` 通道，版本为 `X.Y.Z`。标签必须来自 `master` 历史。
- 手动运行发布工作流：只用于重新发布当前分支的 `ci`，或指定正式版本标签的 `stable`。
- 同一通道发布串行执行。两种架构的测试、构建都成功后才上传。

对象键与公开地址保持一致：

```text
slavesim/<channel>/latest.json
slavesim/<channel>/<version>/release.json
slavesim/<channel>/<version>/<arch>/slavesim-<version>-linux-<arch>.tar.gz
slavesim/<channel>/<version>/<arch>/slavesim-<version>-linux-<arch>-image.tar.gz
```

正式版本禁止用不同提交或资产覆盖。先上传、验证全部版本资产，最后上传 `latest.json`。版本资产长期缓存，入口清单禁止缓存；保留旧版本以支持回退，暂不自动删除。

## GitHub 配置

在 `CcooLcyy/slaveSim` 的 Settings → Secrets and variables → Actions 中设置：

| 类型 | 名称 | 说明 |
| --- | --- | --- |
| Secret | `R2_ACCOUNT_ID` | 与上位机同一个 Cloudflare 账户 |
| Secret | `R2_ACCESS_KEY_ID` | 具有目标桶读写权限的访问密钥 ID |
| Secret | `R2_SECRET_ACCESS_KEY` | 对应的访问密钥 |
| Variable | `R2_BUCKET` | 默认 `mskdsp-update` |
| Variable | `R2_PREFIX` | 默认 `slavesim`，不得使用上位机的 `mskdsp-upper` 前缀 |
| Variable | `R2_PUBLIC_BASE_URL` | 默认 `https://pub-19f3d71852b04011b120b1b814141c12.r2.dev`，不含对象前缀 |

GitHub 不允许回读已有 Secret 的内容，需要安全地配置到 slaveSim 仓库。凭据只进入发布任务环境，设备只访问公开 HTTPS 下载地址，不需要 R2 写入凭据。

R2 使用 S3 兼容接口和 `auto` region，见 [Cloudflare 官方 AWS CLI 文档](https://developers.cloudflare.com/r2/examples/aws/aws-cli/)。

## 更新清单

清单 `schema_version=1`，包含 `project=slavesim`、`channel`、`version`、`commit`、`published_at` 与 `platforms`。

`platforms` 同时含 `linux-amd64` 与 `linux-arm64`，每项包含：

- `url`、`sha256`、`size`：压缩 Docker 镜像包地址、校验值和字节数。
- `image`、`image_id`：镜像标签与 Docker 配置摘要。
- `binary_url`、`binary_sha256`、`binary_size`：二进制包下载信息。

二进制包包含模拟器、主站探针、示例配置、README 和部署工具；不包含真实 `config.json`、日志或凭据。设备按本机架构选择平台，禁止跨架构安装。

## 更新状态与失败处理

更新程序使用 Linux 文件锁防止重复运行，检查同一版本的提交与镜像身份，拒绝通道错误和版本倒退。下载使用临时文件，严格校验大小和 SHA-256，通过后才 `docker load`，并核对导入镜像的 `image_id`。

部署使用 `deploy/compose.release.yml` 与独立镜像环境文件。保留配置、日志和软链接目录。只有运行中容器确实属于对应 Compose 项目与部署目录，才允许自动替换；首次部署需要显式授权参数。

成功标准是新镜像容器运行，且 `/api/state` 返回有效总线与 PTY 路径。成功后才提交本地更新状态；失败恢复旧镜像环境并重建旧版本容器，回退失败明确报错。下载、校验或导入失败时不停止当前容器。

更新会重建 PTY，下位机原串口句柄可能短暂失效，需要由下位机自己的重连逻辑恢复。更新程序不会擅自重启下位机。稳定通道适合长期运行；测试通道会随每次 master 推送更新，应按联调需要启用。

## 验收

1. 两架构构建、协议测试与发布工具测试通过。
2. 上传失败不得更新 `latest.json`；清单只能引用已完整上传并验证的资产。
3. 缺少凭据时发布清晰报错，凭据不出现在源码或日志。
4. 下载损坏、架构不符、清单越界、版本冲突时保留当前运行版本。
5. 新版健康检查失败可恢复旧版；回退保留原配置与日志。
6. 并发更新互斥；重复检查同版本不重建容器。
7. 默认不安装设备定时器，操作者明确执行安装命令后才启用。

## 设备首次启用（本次不执行）

前提是 Linux、Python 3.9 或以上、Docker 与 Docker Compose v2。准备既有 `config.json`，确保其中所有总线的 `link` 都位于指定的软链接共享目录。若已经运行同名容器，需要操作者先确认并完成迁移；更新器会拒绝直接接管原先 `docker run` 或其他 Compose 目录管理的容器。

以下命令从仓库或已校验并解压的二进制包目录执行。`/home/megsky/serial-sim` 仅为示例，必须与现场配置、下位机容器挂载路径一致。初始化不会覆盖配置，也不会启动容器：

```bash
sudo python3 scripts/update.py init \
  --deploy-dir /opt/slavesim \
  --config /home/megsky/slavesim/config.json \
  --serial-dir /home/megsky/serial-sim \
  --log-dir /home/megsky/slavesim/log \
  --manifest-url https://pub-19f3d71852b04011b120b1b814141c12.r2.dev/slavesim/ci/latest.json

# 先检查，再显式进行首次安装；此步会启动 slaveSim 容器。
sudo python3 /opt/slavesim/update.py check --deploy-dir /opt/slavesim
sudo python3 /opt/slavesim/update.py apply --deploy-dir /opt/slavesim --allow-initial-install

# 首次安装成功后再启用自动检查与安装。
sudo python3 /opt/slavesim/update.py install-timer --deploy-dir /opt/slavesim
systemctl list-timers slavesim-update.timer
journalctl -u slavesim-update.service -n 50
```

定时器每 5 分钟检查一次，附加最多 30 秒随机延迟。重复检查同一版本不会重建容器。手动检查或安装分别使用 `check`、`apply`；关闭自动更新执行 `sudo systemctl disable --now slavesim-update.timer`。已初始化的更新脚本与 Compose 模板固定在部署目录，不会被后续镜像更新覆盖，更新这些管理工具需要操作者单独迁移。

正式环境将清单地址改为 `slavesim/stable/latest.json`。稳定清单只会在首次发布 `vX.Y.Z` 标签后出现。已安装的部署禁止自动跨通道切换，应由操作者明确迁移。

## 本地检查

```bash
python3 -m unittest discover -s test -p 'test_*.py' -v
go vet ./...
go test ./...
```

发布工作流同时运行 Python 工具测试与两架构原生 Go/PTY 测试。正式标签示例为 `v0.1.0`，创建标签的行为代表明确发版，不能把 CI 编号当作正式版本。缺少 R2 Secret 时，构建产物仍会保存为 Actions artifact，发布任务明确失败，不会谎报发布成功。
